   cost-complexity pruning, reducing tied scores while staying readable.

Proposed enhancements: allowed as ordinary feature engineering and
standard tabular models, under these conditions.
- 1 Row summaries: allowed. They are row-wise with no fitted parameters,
  and the same code runs on train, validation and test. Any variant using
  train statistics must fit them on train only. Comparing a few
  pre-specified feature sets on validation is model selection; any
  data-driven feature-selection procedure must run on train only.
- 2 Monotone constraints: allowed. Directions must come from training
  labels only, computed in the submitted code rather than hard-coded from
  scratch analyses, and derived within each fold for CV estimates.
- 3-5 Boosting, forest, ExtraTrees, deeper or pruned tree: allowed.
  Hyperparameters may be chosen by train CV or on validation. Early
  stopping on validation passes validation data into fit, so treat it as
  a gray area and avoid it unless the instructors confirm it. Choose
  boosting rounds by train CV or as a grid value compared on validation.
- 6 Out-of-fold logistic-regression feature: allowed under "other
  standard tabular models and ensembles", which resolves the earlier open
  question. Fit it and any scaler on train only; validation and test get
  scores from the train-fitted model. Entity repeats inside train may make
  out-of-fold scores look stronger than validation or test scores. That
  is a methodological risk, not a rule issue. Declare it in the report.
  Superseded 2026-09-19: the user ruled out linear models, so this
  feature is not allowed and was removed from experiments.py.
- 7 Seed averaging and equal-weight averaging: allowed. Average
  probabilities row by row instead of rank-averaging across test rows, so
  no transform depends on the test set and outputs stay within [0, 1].
  Blend weights or a meta-model fitted on validation labels would be a
  model fitted on validation, which Section 4 does not allow.
- Protocol: allowed. Train CV fits and tunes; validation compares
  finalists, makes the final selection and supports bootstrap evaluation.
- Withdrawn: the earlier train-versus-validation distribution comparison.
  It falls outside validation's listed roles, and a fitted classifier
  separating the splits would be a model fitted on validation. Any test
  involvement is prohibited. Ask the instructors before reviving it.
Out of bounds for all future work:
- Pretrained tabular models such as TabPFN (downloaded weights), external
  data, and attempts to identify the source dataset or embedding model.
- Reconstructing hidden entities or source observations, for example by
  clustering rows into identities or propagating labels through shared
  observations across pairs.
- Using row_id or row order as features. Using test.csv for anything but
  generating predictions: no test statistics, pseudo-labels or
  clustering. As a conservative reading, also avoid transforms that
  depend on other test rows, such as rank averaging.
- Leaderboard probing, more than five submissions a day, or manual edits
  to prediction files. Select models on validation, not the public board.
- Sharing code, engineered features or predictions with other teams, or
  publishing competition data. Keep any repository private, without CSVs.
- Calibration fitted on validation. Monotone calibration cannot improve
  ROC-AUC anyway.
Requirements for the future submission code:
- Read test.csv only in the prediction step. Apply the same row-wise
  feature code and the train-fitted models; never refit on train plus
  validation.
- Assert that each test row_id appears exactly once and matches
  sample_submission.csv, and that targets are finite and within [0, 1].
  Write the file from code and record the designated submission.
- Keep all three model families in the final comparison, even if the
  final submission is an ensemble.

Design, with the reason for each change
- CV: RepeatedStratifiedKFold, 5 folds x 2 repeats, random_state 42, on
  train only. The same 10 folds serve every configuration, so comparisons
  are paired. Selection rule at every stage: highest mean fold AUC. The
  stopped first run used 3 repeats (15 folds).
- Stage 1, calibration: the three baselines under CV. Reason: check that
  CV scores can stand in for validation before relying on them.
- Stage 2, feature ladder at baseline settings, one change per step:
  (1) add the row mean; (2) add six row summaries: mean, median, mean of
  log1p, std, max, and coefficient of variation std/mean, set to 0 for an
  all-zero row; (3) forest only, max_features 0.2 so the few summary
  columns are considered at more splits; (4) monotone constraints.
  Reason: one aggregate carries most of the signal, and trees combine
  many weak signals poorly. Summaries are row-wise with nothing fitted.
- Monotone directions are computed inside each fit from its own rows: -1
  or +1 by the sign of the column's AUC minus 0.5, and 0 (unconstrained)
  when that gap is within two null standard errors, computed as
  sqrt((n1+n0+1)/(12*n1*n0)). Reason: all 512 features fall monotonically
  in train; constraints should limit overfitting and label-noise effects.
- Stage 3, grids on each family's best ladder step, which fixes the
  feature set and constraint setting. Tree: depth 3-6 x min leaf 10/20/30
  x ccp_alpha 0/0.001/0.003 (36 configs). Forest: RF or ExtraTrees x
  max_features sqrt/0.2 x depth 3/6/10/None x min leaf 1/10/30, 300 trees
  (48). Boosting: learning rate 0.03, subsample 0.8, depth 1/2/3 x
  colsample 0.3/0.7 x weak (min_child_weight 1, lambda 1) or strong
  (10, 10) regularisation (12). Boosting rounds are chosen by CV, scored
  every 50 rounds up to 3000 from one fit per fold. Reason: the baselines
  were shallow and untuned; depth 1-2 boosting builds an additive model.
- Stage 4, feature re-check at tuned settings: each family's tuned config
  is also scored with the other combinations of raw or raw+summaries
  features and monotone constraints off or on; boosting re-chooses its
  rounds. The best by CV continues. Reason: stage 2 tested these changes
  only on the untuned baselines, a weak test for tuned models. This
  stage replaced the removed logistic-regression stage.
- Stage 5: seed averaging over seeds 42-46 for the forest and boosting
  finals, then an equal-weight average of their probabilities. Reason:
  lower variance without blend weights fitted on any labels.
- Stage 6: the baselines are refitted exactly, and the four enhanced
  finalists (tree, forest, boosting, ensemble) are fitted on all train
  rows and scored once on validation. A stratified bootstrap with 2000
  resamples gives intervals and paired differences against each family
  baseline and the XGBoost baseline. The highest validation AUC among the
  enhanced finalists is recorded as the candidate.
- CV tasks run in parallel over (configuration, fold) with joblib and one
  thread per model, so results do not depend on thread counts.
